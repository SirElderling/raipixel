# PNG compression experiment register

Last reviewed: 2026-10-16. Scope: PR [#2](https://github.com/SirElderling/raipixel/pull/2), branch `feat/raster-foundation`. This is the **index of record** for hypotheses, measured candidates, regressions and follow-up gates. New work must **consult and update this file** before rerunning an algorithm that is already known to fail on the same codec and corpus.

The goal is the **smallest lossless interoperable PNG within bounded time and memory**, while retaining a separate fast writer. Experiments are diagnostics until promoted through correctness, memory/work accounting, and three-platform tests. The Rust `png 0.18.1` crate is used **only through its public interfaces as a black-box reference**. Never inspect/copy its implementation. Production implementation remains safe stable Rust 1.99.1 without new runtime dependencies.

## Fixed corpus and comparison rules

- `icon-64-compressed.png`: original four-color 64×64 case, SHA-256 `45c209032c94af8bd9ded7476f7c9839deb8520d164719a12856e2f54a7e88de`.
- `sheet-1024-compressed.png`: generated four-color sprite sheet, SHA-256 `4e329be91b53193666195066b19022a2e956f4895f616b5ebadb31d05375d44a`.
- `comparison-sheet-1024.png`: independently authored mixed-filter five-color sprite sheet, SHA-256 `b2212db9b942357462ccfefeb69b8312388738300aed2272b21fce24e7bf3d0a`.
- Additional coverage: incompressible 256-noise, textured 1024, odd scanlines (7×11, 13×11, 17×11, 257×7), 1024×300 crossing 65,535-byte DEFLATE chunks, 1/2/4/8-bit palettes, alpha-zero hidden RGB and >256 exact colors.
- Always compare actual PNG byte lengths, whole-encode times including palette building/output allocation, compiler, checksum verification, complete decoded RGBA including hidden RGB, determinism, negative CRC case, unsupported-image behavior, resource/work accounting and binary/heap impact. Calibrate at least 25 ms per timed batch, alternate/rotate samples, and report medians/ratios **per platform**. A reference default writer with better compression is **not** equivalent to its Fast mode.
- Independently ground each new accepted candidate using the public reference decoder before production promotion; the raipixel decoder alone is insufficient. `Work::remaining()` equality **does not prove** the candidate's extra scratch memory/CPU were realistically charged.
- Record script + Git commit SHA, input SHA, OS/CPU, rustc, source and driver hashes, trials, measured output, status, decision and unanswered safety questions. Keep the original raw CI logs linked. Never silently overwrite a prior measurement with a new environment's result.

## C11 first native measurements — revision `58c3fcaa`, Rust 1.99.1

The experiment uses bounded rolling 32 KiB history, 4 KiB dynamic-Huffman gate, a deeper recent-match chain and optional indexed row filters. **Every one of the seven candidates** is verified against complete RGBA using the accepted decoder, checked against deterministic output, tested for deliberately invalid IHDR CRC, and charged the same *reported* Work as baseline. The generated fixtures are independently constructed from predeclared RGBA values, including nonzero RGB behind alpha=0. This is correctness screening, **not** independent external-decoder certification or fair resource accounting.

| Case | Current | Dynamic depth16 | Dynamic depth32 | Dynamic depth64 | Dynamic depth32+Sub | Winning measured output |
|---|---:|---:|---:|---:|---:|---|
| Icon 64 | 172 | **157** | **157** | **157** | 160 | 157 (depth16/32/64) |
| Generated sheet 1024 | 4,396 | 2,308 | 1,683 | **1,668** | 2,503 | 1,668 (depth64) |
| Original sheet 1024 | 9,912 | 4,074 | 3,644 | **3,629** | 4,027 | 3,629 (depth64) |
| Independent 256-color 257×7 | 1,451 | 1,451 | 1,451 | 1,451 | **1,175** | 1,175 (Sub) |
| Independent 3-color 1024×300 | 1,006 | 761 | 799 | 800 | **729** | 729 (Sub) |
| One-/three-/five-color tiny odd widths | 119 / 142 / 164 | unchanged | unchanged | unchanged | equal or worse | baseline/None |

On **Windows**: generated sheet accepted **3.63 ms**, depth64 **4.95 ms** (1.37×); original sheet **4.39 → 6.66 ms** (1.52×).
On **Linux**: generated sheet **4.01 → 5.43 ms** (1.35×); original sheet **4.83 → 7.11 ms** (1.47×). Absolute CPU times vary by host and run.

Deepening from 32 to 64 improved each large sheet only another **15 bytes** (~0.9% of the 32-depth generated output; ~0.4% original) while taking modest additional time; blindly searching 128/256 matches is **not currently justified** without an intermediate cost-aware matching hypothesis. Even depth64 performs worse than depth16 on 1024×300, emphasizing the case for opt-in size-based candidate selection over universal deeper-search defaults. This result **does not establish general PNG parity** outside this limited set of images.

**Status (16 October 2026):** Linux, Windows and macOS ARM64 all completed successfully; full candidate verification passed across all three. Source records: [native run](https://github.com/SirElderling/raipixel/actions/runs/38932675423). No application runtime code changed.

### Fixed target and current gaps

Same indexed inputs: `png 0.18.1` default = **1,545 B** generated / **3,552 B** independent. **Frozen baseline C11 fallback:** depth64 rolling history with guarded dynamic Huffman and None filter: **1,668 B** generated (+8.0% vs reference) and **3,629 B** independent (+2.2% vs reference). **New best validated C12 output:** depth64 + one-step lazy matching + dynamic Huffman + None filter, **1,653 B** generated (+7.0% vs reference) and **3,570 B** independent (+0.51% vs reference). Preserve *both* byte counts and source recipes. The smaller candidates now pass self-decoder RGBA/CRC/determinism checks on all three OSes but are **not yet production-qualified**, externally decoded, or fully resource-accounted. Keep exact source and benchmark fixture hashes to make any future regression detectable. Quality-first compression may spend more milliseconds, but must honor deterministic bounded time/work/heap and must not create unacceptable pathological cases.

## C12 completed: lazy parsing beats cost-aware heuristic

[Native run 38943652827](https://github.com/SirElderling/raipixel/actions/runs/38943652827) passed on all three target platforms with **identical sizes**. The 64-deep bounded rolling-history matcher, dynamic Huffman and **one-step lazy parsing** is the current size leader: icon **157 B**, generated sheet **1,653 B**, original sheet **3,570 B**. Generated reference default **1,545 B**, original **3,552 B**. This is the new **best-known experimental fallback** (not production ready). The depth64 non-lazy C11 implementation remains a preserved fallback and independent control.

| C12 strategy | Generated 1024 | Original 1024 | Interpretation |
|---|---:|---:|---|
| C11 depth64 greedy | 1,668 | 3,629 | Preserved baseline |
| Depth64 with fixed-Huffman bit-cost proxy | 1,668 | 3,629 | **No gain; reject** on this corpus |
| Depth64 with one-step lazy parsing | **1,653** | **3,570** | **Accept as size champion (scratch only)** |
| Depth64 lazy + fixed-code cost proxy | 1,653 | 3,570 | **No additional gain, slower; reject** |

Linux encoding: generated **4.03 → 4.18 ms** (depth64 → lazy64), original **5.51 → 5.95 ms**. Windows **4.07 → 4.19 ms**, original **5.62 → 5.90 ms**. macOS ARM64 **4.29 → 4.19 ms**, original **5.89 → 6.25 ms**. These are separate median measurements, not latency promises. On independently generated 1024×300, the older depth16 produced **761 B** versus lazy64 **800 B**; preserve multiple *algorithm candidates* for adaptive best-of-N rather than forcing lazy64 everywhere.

**C12 source reproducibility:** experiment test `tools/png_cost_parse_trial.py` from [run head `1c4cd095`](https://github.com/SirElderling/raipixel/commit/1c4cd0952d8e363c6ec81acc7fed59bf10514b10) (native CI SHA). Exact candidate implementation SHA-256 appears in its per-platform JSON line under `hashes.c64lazy`; all fixture hashes are in the CI output. The C12 harness enforced that no new candidate would regress the C11 size floors for principal images. The C12 generated candidate must undergo independent reference decoding, allocation/work accounting and adversarial testing before any production promotion.

**C13 selection benchmark design:** this experimental encoder generates and validates all seven entire PNG files, selects the shortest with a stable first-minimum tie-break, and independently times the full seven-encode selection path. Its fallback constraints cover **both** large sprites and the C11 Sub-winning odd-width/block-boundary cases, avoiding regressions from choosing a single fixed strategy. Existing C11/C12 and reference trials remain available through manual GitHub Actions dispatch, but do not rerun on every push.

### Next experiment queue (ordered, change-controlled)

1. **Correct validation coverage** for C10 and C11, then collect native 3-OS evidence and write measured outcomes here. If new candidate fails exact RGBA/CRC/Adler, stop without benchmarking it.
2. **If C11 shows positive size gains**, screen an adaptive best-of-N policy: for each exact RGBA input, compare retained candidates, return the smallest and charge actual work. Include small palette, odd width, incompressible and cross-block cases.
3. **If depth reaches diminishing returns**, test one-step *cost-aware* LZ parsing using lengths/distances + actual Huffman code costs. Compare against C11 without changing filter/palette. Stop if no material size win.
4. Only then attempt a bounded, fallible-memory **production opt-in maximum encoder**, with fresh independent decoding tests and exhaustive preflight/resource accounting. No API/default behavior changes until this gate passes.

**Repetition guard:** Before coding, search this register and [the candidate notes](candidates/) for the same idea, compressor mode, corpus and search depth. Avoid duplicate runs on unchanged SHA/fixtures. If a trial is rejected, require a different causal condition (e.g. Sub *with dynamic Huffman* instead of Sub *with fixed Huffman*) and name that difference. Distinguish *queued*, *failed*, *rejected*, *promising*, *validated* and *promoted* statuses. Do not cherry-pick one file or one OS to make a generic claim.
