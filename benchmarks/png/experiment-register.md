# PNG compression experiment register

Last reviewed: 2026-10-16. Scope: PR [#2](https://github.com/SirElderling/raipixel/pull/2), branch `feat/raster-foundation`. This is the **index of record** for hypotheses, measured candidates, regressions and follow-up gates. New work must **consult and update this file** before rerunning an algorithm that is already known to fail on the same codec and corpus.

The goal is the **smallest lossless interoperable PNG within bounded time and memory**, while retaining a separate fast writer. Experiments are diagnostics until promoted through correctness, memory/work accounting, and three-platform tests. The Rust `png 0.18.1` crate is used **only through its public interfaces as a black-box reference**. Never inspect/copy its implementation. Production implementation remains safe stable Rust 1.99.1 without new runtime dependencies.

## Fixed corpus and comparison rules

- `icon-64-compressed.png`: original four-color 64×64 case, SHA-256 `45c209032c94af8bd9ded7476f7c9839deb8520d164719a12856e2f54a7e88de`.
- `sheet-1024-compressed.png`: generated four-color sprite sheet, SHA-256 `4e329be91b53193666195066b19022a2e956f4895f616b5ebadb31d05375d44a`.
- `comparison-sheet-1024.png`: independently authored mixed-filter five-color sprite sheet, SHA-256 `b2212db9b942357462ccfefeb69b8312388738300aed2272b21fce24e7bf3d0a`.
- Additional coverage: incompressible 256-noise, textured 1024, odd scanlines (7×11, 13×11, 17×11, 257×7), 1024×300 crossing 65,535-byte DEFLATE chunks, 1/2/4/8-bit palettes, alpha-zero hidden RGB and >256 exact colors.
- Always compare actual PNG byte lengths, whole-encode times including palette building/output allocation, compiler, checksum verification, complete decoded RGBA including hidden RGB, determinism, negative CRC case, unsupported-image behavior, resource/work accounting and binary/heap impact. Calibrate at least 25 ms per timed batch, alternate/rotate samples, and report medians/ratios **per platform**. A reference default writer with better compression is **not** equivalent to its Fast mode.
- Independently ground each new accepted candidate using the public reference decoder before production promotion; the raipixel decoder alone is insufficient. `Work::remaining()` equality **does not prove** the candidate's extra scratch memory/CPU were realistically charged.
- Record script + Git commit SHA, input SHA, OS/CPU, rustc, source and driver hashes, trials, measured output, status, decision and unanswered safety questions. Keep the original raw CI logs linked. Never silently overwrite a prior measurement with a new environment's result.

The generated fixtures are independently constructed from predeclared RGBA values, including nonzero RGB behind alpha=0. ## C14 final verdict: per-row signed-magnitude heuristics rejected

[Native CI 39003749300](https://github.com/SirElderling/raipixel/actions/runs/39003749300) completed successfully on three OSes. Every candidate passed both raipixel's own decoder and the public `png 0.18.1` decoder, including all exact RGBA samples and alpha-zero RGB. The signed-magnitude row score did not select a better whole-file output than fixed global None/Sub on any test fixture. Both 64-byte sample and available-row scoring returned **1,673 B** for generated 1024, versus global lazy None **1,653 B**. ## Production gate: explicit scratch bounds and work accounting (C15 follow-up)

The experimental candidates are **not** safe-to-promote product code despite passing roundtrips. Static inspection of the scratch code gives the following **major backing-buffer capacities**, for a full 65,535-byte DEFLATE block and 32 KiB history. These numbers describe intended maximum element counts, **not empirically measured heap peaks**, and exclude allocator overhead, short-lived Huffman tree/heap/RLE/code buffers, full-file selected output(s), and the input image.

| Temporary buffer | Capacity (bytes) |
|---|---:|
| Packed raw block | 65,535 |
| Previous-history + raw input joined | 98,303 |
| Existing encoder dictionary (8,192 `u32`) | 32,768 |
| Additional hash heads (8,192 `u32`) | 32,768 |
| Per-position hash-chain links (98,303 `u32`) | 393,212 |
| Fixed encoder output reservation (`BLOCK*9/8+16`) | 73,742 |
| Packed literal/match tokens (up to 65,535 `u16`) | 131,070 |
| Retained rolling history | 32,768 |
| Two 4,096-byte indexed rows (8-bit, max width) | 8,192 |
| **Known listed backing buffers only** | **868,358 B (~848 KiB)** |

Those buffers and intermediate Huffman structures are currently created with `Vec::with_capacity`, `vec![]`, `.push` or `.extend` without a fully fallible reusable workspace. A production opt-in encoder must make all allocations explicit/fallible and limit individual allocations and aggregate peak including **one current output and one retained best output**; it must not keep all candidate PNGs in memory as the diagnostic test does. A heap-cap implementation should be verified on 32-bit/64-bit targets using `size_of`, `capacity()` and allocation-failure tests; the static estimate alone is **not a certified memory bound**.

The existing indexed writer charges `raw_size*16 + ceil(raw_size/65535)*8256` work units per pass (plus pixel palette scan). It does **not** charge the new depth-64 chain traversals or lazy lookahead. At 4,096×4,096 with 8-bit indexed pixels: `raw_size=16,781,312 B`, `blocks=257`, existing charge **270,622,784 units for one pass**, **1,353,113,920 units for five** or **1,894,359,488 for seven**, exceeding default `MAX_WORK=1,000,000,000` even *before* the extra search work. For a four-bit 1,024×1,024 sheet: 525,312 raw bytes and **8,479,296 charged units per pass**, **42,396,480 for five**, again excluding the substantially heavier chain matching. Do **not** interpret equality of `Work::remaining()` in prior trials as adequate billing.

**Minimum acceptable implementation policy:** a single reusable workspace per operation; explicit checked raw-size/heap/output-size arithmetic; preflight total output staging/algorithm budget before touching the caller's writer; charge the actual bounded match attempts/byte-comparisons (not a pretended unchanged baseline) or use a conservative explicit preflight search ceiling; store at most a best and a current PNG; stable minimum-size selection; low-budget and allocation-failure tests; no unsafe, assembly, FFI or production dependencies. On insufficient budget fail without writing bytes or skip optional candidates via a documented deterministic policy; never leave partially written output due to budget failure. Only a true output-I/O error may leave partial bytes under existing writer contracts. Keep the existing `encode`, `encode_compact`, and `encode_indexed` APIs/byte contracts untouched until a new explicit opt-in passes these gates.

**C16 additional generalization screen:** now includes 15 reproducibly generated pixel-art samples with different palette cardinalities (including 257 exact RGBA values), scanline transitions, transparent RGB and DEFLATE boundary behaviors. Failure of five-mode byte equality on these *new* samples is a legitimate optimization counterexample, **not a PNG correctness failure**; report file-size regret and selected mode transparently. Do not suppress counterexamples or merge C16 findings with the frozen C15 corpus.
